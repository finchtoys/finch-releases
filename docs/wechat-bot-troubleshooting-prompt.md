# 微信 Bot 发送失败排障 Prompt

将以下内容复制给出现问题的用户的 Finch：

---

请帮我定位并尝试修复本机「微信 Bot」小程序。Finch 通过 `wechat_send` 向微信发送消息时返回：

```text
Failed to send WeChat message: sendMessage ret=-2 prepare failed
```

不要直接认定是未登录、SDK 初始化失败、网络断开或限流。该错误通常意味着 iLink `sendmessage` 接口返回了业务失败，需要结合实际代码和响应分析。

请按以下步骤执行：

## 1. 找到实际运行的小程序

先加载 `finch-mini-tool-creator` skill，使用 `MiniTool list/status` 确认微信 Bot 的真实 id、版本、安装作用域和运行状态。检查个人目录 `<finchHome>/.finch/extensions/` 和全局目录 `~/.finch/extensions/` 下对应安装包；不要硬编码用户名、Finch Home 或目录名。若两处都有，确认当前实际加载哪份。

读取 `package.json`、`finch.json`，根据 `main` 定位运行入口，通常为 `dist/index.js`。安装包可能没有 `src`；只改源码而不更新运行 dist 不会生效。目录未授权时先请求授权，遇到拒绝立即停止。

## 2. 沿代码追踪

搜索 `wechat_send`、`sendMessage`、`ilink/bot/sendmessage`、`context_token`、`ctoken:`、登录和退出逻辑，检查：

- 收件人是否来自当前登录账号，而不是旧映射；
- `context_token` 是否存在、是否由最近入站消息更新；
- 缓存是否按当前 bot 身份隔离；
- 退出或重新登录是否遗留旧上下文；
- 服务端 `ret`、`errcode`、`errmsg` 是否被完整检查和呈现。

只记录 token 是否存在、更新时间等诊断信息，不输出凭证、token 值、完整请求体或私人消息。必要时查相关日志，但不要把整份敏感日志读入对话。

## 3. 先验证再改

我授权向当前已绑定的本人微信发送一条“Finch 微信发送测试”，不向其他人发送。先记录结果；若需要我从手机向当前 bot 发一句话，请提示我操作，确认 Finch 收到后再重测。比较前后结果，区分缺失上下文、陈旧上下文和其他服务端问题，不编造 token 有效期或声称 `getconfig` 能刷新 token。

## 4. 有证据后尝试最小修复

修改前备份实际运行入口，保留回滚路径。优先补足安全的错误诊断，避免只返回 `ret` 而遗漏 `errcode`。

若确认是旧上下文问题，修正缓存生命周期或账号隔离。若考虑针对 `ret=-2` 且 `errmsg` 为 `prepare failed` 的情况不携带旧 `context_token` 重试，只能作为待验证的兼容策略：最多一次，复用 `client_id`，不扩大到所有 `-2` 错误，不对网络超时盲目重发，不把失败改成成功。没有上下文时给出“请先从微信给当前 bot 发消息”的明确提示。

不要改认证协议、伪造 token、清空全部存储、删除聊天记录或卸载小程序。dist 是打包文件时先读对应片段，再做唯一匹配的局部修改，不要整包重写。

## 5. 检查并重载

执行适用的语法检查；有源码和构建环境时再做类型检查与构建。使用 `MiniTool reload` 重载确认的真实 id，然后通过 `wechat_send` 重测。若当前会话工具仍使用旧实例，说明需要新回合或重启后验证，不要宣称修复成功。修改无效或导致加载异常时恢复备份并重载。

## 6. 汇报

简短列出：实际安装路径和版本、已确认事实与推测、修改点、备份/回滚方式、测试结果。未经真实发送验证只能说“已修改，待验证”。说明直接修改安装目录是临时热修复，更新或重装可能覆盖；不要自动发布或上传日志。
