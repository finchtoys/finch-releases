# `ret=-2 / prepare failed` 诊断（2026-11-15 巡检复发）

范围：`extensions/wechat-bot` 0.6.0。本轮**未**发送微信消息、未改业务源码、未重新登录、未清 token、未发包。

本轮结论建立在 2026-10-14 的深入调查之上（`.finch/research/weixin-20261014/investigation.md`），
只补本次复发的证据与一处口径纠正，不重复抄写已有结论。

## 0. 先纠正一个流传的说法

**「context_token 已经去掉了」不成立。**

现状是兜底而非移除：`src/media.ts:150-155` 正常发送带 `context_token`；命中
`isStaleTokenError`（`src/media.ts:99-101`，判定 `ret === -2 && errmsg =~ /^prepare\s*failed$/i`）
时在 `src/media.ts:186-190` **去掉 token 重试一次**。

本次巡检**带 token 与去 token 两条路径都试过，都被拒**（诊断号 `f8701be3-…` / `3330b8d2-…`）。
所以问题不在 token 字符串本身——兜底路径本身就是失败的。

## 1. 已排除

| 假设 | 依据 |
|---|---|
| context_token 过期 | 去 token 重试同样被拒。上游 issue #331 说该字段可选，去掉后仍失败，说明服务端拒绝的不是 token 值。 |
| 文本过长触发 | 上游 #284 的控制变量案例是 7337 字符才失败。本次正文很短。且 0.6.0 已有分段：`src/text-chunks.ts`（4000 字符 / 4000 UTF-8 字节双限），`src/media.ts:328-336` 发送前切块。 |
| errmsg 被客户端吞掉 | `errmsgSafe`（`src/media.ts:110-125`）本次放行，回执里 `errmsg=prepare failed` 是服务端原文，不是 `server rejected request` 兜底标签。可观测性这条本次没有恶化。 |
| 登录态失效 | 登录失效是 `ret=-14`（`src/media.ts:139-141`），本次是 `-2`。 |

## 2. 已证实

**发送资格与「最近入站时间」强相关，这是最贴近本机的解释。**

2026-10-14 记录的本机对照证据：同一正文在上下文更新后 31 秒发送成功；失败时距最新入站约
**46.70 小时**。上游 #309 是同一现象的独立现场（定时推送在长时间无入站后失败，新用户消息后恢复）。

本次巡检是**bot 主动推送**，且发生在长时间无入站之后——与上述模式一致。

**注意这是相关性证据，不是因果证明。** `receivedAt` 是客户端捕获时间，不是服务端 token 签发时间
（`src/context.ts:74`），因此不能推出精确 TTL，也不能排除服务端账号/配对/风控状态（上游 #268
有换 bot、重绑都不恢复的账号级案例）。

## 3. 未定位（缺什么证据）

1. **服务端对「主动推送窗口」的真实判据**。要区分「token 年龄」「peer 会话窗口」「账号级状态」三者，
   需要一次受控对照：同一账号、同一收件人，分别在入站后 1h / 12h / 30h / 48h 各发一次短文本。
   这需要真实发送，**须舜子授权且只对他的会话做**。
2. **是否存在可用的服务端预检接口**。当前 `assertCanSend`（`src/media.ts:89-92`）只校验本地有无上下文，
   不校验新鲜度，等于没有预检。上游是否提供查询发送资格的接口，未核。

## 4. 确定的客户端缺口：有信号，没用

`context.receivedAt` 一路传到观测记录（`src/media.ts:208` 的 `contextReceivedAt`），
但**发送前从不检查它**。结果是：明知上下文已经很旧，仍然盲发、盲失败，用户只能在事后从错误里猜。

建议的修法（**行为变更，等舜子拍，未实施**）：

- 发送前比较 `now - context.receivedAt`，超过阈值时**不再盲发**，直接返回一条可执行的提示：
  「微信侧主动推送窗口已过期，请在微信里先给 bot 发一条消息」。
- 阈值取多少需要上面第 3.1 项的受控数据；在拿到数据前，宁可把阈值设得保守（例如 24h）并在
  超限时**仍然尝试发送**、只是把提示附在失败信息里，避免把本来能成功的推送误杀。
- 巡检这类定时任务应把「上下文过旧」当作**预期内的降级**，与真实故障分开上报，不再每天推一条失败。

## 5. 舜子现在能做什么恢复推送

在微信里**先给 bot 发一条任意消息**重建上下文，之后重发即可——这与 2026-10-14 那次
「上下文更新后 31 秒同正文发送成功」的现象一致。不需要重新扫码，也不需要清 token。
